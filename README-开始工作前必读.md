# 学习宝项目开始工作前必读

> 适用于项目所有参与者：项目所有者、Codex、DeepSeek、GLM 及其他 AI 窗口。
>
> **每次开始任何操作前，必须完整阅读本文档。**

## 1. 开工确认

执行者在第一条进度消息中必须明确写：

```text
已阅读《README-开始工作前必读.md》，本次任务范围是：...
```

没有这条确认，不得开始修改代码。

## 2. 先看留档，再按需读代码

默认禁止每轮重新扫描整个项目。按以下顺序获取上下文：

1. 阅读本文档。
2. 阅读 `docs/ops/INDEX.md` 中的当前任务索引。
3. 阅读与本次任务相关的操作留档。
4. 检查 `git status --short --branch` 和与本任务相关的 diff。
5. 只读取本次点名文件、diff 涉及文件及它们的必要直接依赖。

只有以下情况可以做全局扫描：

- 正式版本发布前验收。
- 安全审计或敏感信息检查。
- 依赖、数据库或整体架构迁移。
- 定向证据不足以判断问题根因。

## 3. 每个窗口必须独立负责

- 一个窗口只处理一个明确范围。
- 不得顺手重构与本任务无关的模块。
- 多窗口并行时，优先使用独立分支或 Git worktree。
- 两个窗口需要修改同一文件时，必须先明确执行顺序，不允许同时写入。
- 不得撤销、覆盖或格式化其他窗口的未完成改动。

## 4. 每次操作必须留档

留档位置：

```text
docs/ops/
├── INDEX.md
├── active/
└── archive/
```

开工时在 `docs/ops/active/` 建立简短记录，任务完成后移入 `docs/ops/archive/`。

每份留档只保留以下高信号内容：

```markdown
# 任务名称

- 执行时间：
- 执行窗口：
- 任务目标：
- 允许修改的文件：
- 实际修改的文件：
- 验证命令与结果：
- Commit：
- Push：
- 遗留风险：
- 下一步：
```

留档是后续窗口的主要上下文，不写长篇流水账。

## 5. Git 提交与推送规则

完成一个边界清晰、验证通过的单元后，应尽快：

1. 检查真实 diff。
2. 检查敏感文件和无关文件。
3. 运行与改动区域匹配的测试。
4. 创建单一职责的 commit。
5. 推送当前分支。
6. 在操作留档中记录 commit hash 和 push 结果。

不得提交或推送：

- 未通过验证的半成品。
- 混合了多个无关任务的改动。
- `.env`、真实密钥、数据库、上传文件、日志、`node_modules`、虚拟环境、`dist`。
- 验收截图、临时文档或本地测试产物。

## 6. 验证命令

前端改动至少运行：

```powershell
cd frontend
npm.cmd run lint
npm.cmd run test -- --run
npm.cmd run build
```

后端改动至少运行：

```powershell
backend\.venv\Scripts\python.exe -m pytest backend\tests -q
python scripts\security_check.py
```

只修改文档时，至少运行：

```powershell
git diff --check
```

## 7. 版本公告规则

- 普通实现窗口不同时修改版本公告。
- 发布或总控窗口统一汇总已完成的功能和修复。
- 公告言简意赅，只写用户能感知的变化。

## 8. 规则本身如何优化

任何人或 AI 发现本文档存在以下问题时，都必须告诉项目所有者：

- 规则导致重复工作或浪费大量时间。
- 规则与当前工具链或项目架构不再匹配。
- 规则不足以防止代码覆盖、敏感文件泄露或无法回退。
- 存在更简单、更可验证的替代流程。

提出优化时必须说明：

1. 当前问题。
2. 建议怎么改。
3. 对现有窗口和 Git 流程的影响。

未告知项目所有者前，不得悄悄改变这份规约的核心规则。

## 9. 收尾确认

每次任务结束时，执行者必须输出：

- 实际修改文件。
- 验证命令和真实结果。
- 是否可以提交。
- 是否已提交和推送。
- 对应操作留档路径。
- 剩余风险和下一步。
